# S1 · RAG 与 LLM 应用评估 — 召回调优记录

本文件记录 S1 节点在 Dify 知识库上的召回质量测试与调优过程。
目标是验证「指标选择理由」和「失败样本标注」两项能力信号。

## 环境基线

- Dify: 1.10.1-fix.1（腾讯云 Lighthouse，2C4G）
- LLM: Qwen2.5-7B-Instruct Q4_K_M（AutoDL Ollama，RTX 3080 Ti）
- Embedding: bge-m3（Ollama）
- 知识库: ai-career-graph-docs（nodes.md / edges.md / ADR-001~004 / PROOF_OF_WORK.md）
- 切分: 512 / 重叠 100 / Markdown 解析
- 查询: "M1 迁移规则的工件是什么，在 A2 的哪个环节被消费？"

## 测试 1 · 纯向量检索（失败样本）

- 检索模式：向量检索
- 参数：Top K=3，Score 阈值=未启用
- 结果：M1=0.58，M2=0.57，M4=0.57
- **问题**：三条迁移边的分数几乎相同，M1 对 M2 的领先仅 0.01。
- **根因**：`M1`/`M2`/`M4` 是硬标识符，在图谱文档中三条边的文本结构
  高度相似（迁移规则 + 工件 + 消费环节），纯语义向量无法区分 ID 本身。
  查询中的 `M1` 字符串没有对应的语义信号，向量模型只能依据上下文
  相似度打分，导致三条边落在同一分数区间。

## 测试 2 · 混合检索

- 检索模式：混合检索，语义 0.7 / 关键词 0.3
- 参数：Top K=3，Score 阈值=未启用
- 结果：M1=0.49，M2=0.43，M4=0.42
- **变化**：M1 对 M2 的领先从 0.01 扩大到 0.06。
- **分析**：关键词通道正确命中了 `M1` 这个精确字符串，将其从
  "三条几乎同分的边"中拉出。绝对分数下降（0.58→0.49）是混合融合
  刻度的正常表现，不代表效果变差；判断标准是**区分度**而非绝对分。
- **结论**：在当前 Top K=3~5 的召回场景下，0.06 的领先足以让 M1
  稳定排第一。混合检索是本场景的正确选择。

## 指标选择理由

- **为什么用混合检索而不是纯向量**：知识库包含 `A1`/`M1`/`S2` 等
  硬标识符，纯语义通道对这类标识符的区分度接近零（测试 1 已量化）。
  关键词通道提供精确匹配补偿。
- **为什么关键词权重设 0.3 而不是 0.5**：0.3 已足以让 M1 拉开 0.06
  的差距；更高的关键词权重会牺牲自然语言查询的语义召回能力。0.3 是
  "精确匹配够用、语义理解不退化"的平衡点。
- **为什么 Score 阈值未启用**：当前知识库规模小（数个文档），
Top K=3 已是强约束，阈值的过滤作用有限。实测数据也说明风险：
混合检索下 M1 分数 0.49，若沿用纯向量时代的 0.5 阈值会把正确
答案过滤掉——阈值必须与检索模式的融合刻度匹配。待知识库扩大、
召回噪声上升时，再以实测分数分布为依据启用阈值。

## Rerank 部署判断

**结论**：当前暂不部署 Rerank 模型。

**技术可行性**：
- RTX 3080 Ti (12GB) 总占用估算：Qwen2.5-7B Q4 ≈5.9GB +
  bge-m3 ≈1GB + bge-reranker-v2-m3 FP16 ≈2.2GB ≈ 9.1GB，
  余量约 2.4GB，**可以部署，不会 OOM**。
- Reranker 为 Cross-Encoder，通过 FlagEmbedding/Xinference 以独立
  Python 进程加载，**不经过 Ollama 的多模型调度**，不触发模型换出。

**暂不部署的理由**：
- 当前 Top K=3~5、M1 已稳定排第一，reranker 的边际排序收益有限。
  Rerank 解决的是"正确片段在候选池但排序靠后"，而 M1 已排第一。
- 优先将时间投入 A1/S2 的证据生产。

**触发部署的条件（未来）**：
- Top K 扩大到 10+ 后，正确片段仍频繁落在 5 名之后；
- 知识库文档量显著增加导致召回噪声上升；
- 或改用云端 Rerank API（不占本地显存）。
